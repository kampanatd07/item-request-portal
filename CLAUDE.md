# Project: Item Request Portal

## What this is
Web app where staff at 4 Carabao Group plants (CBD, APM, APG, ACM) request new
non-stock and service purchase items. It checks duplicates, suggests the category,
composes the standard name, issues a central 11-digit code from the group's
running register, and exports AX/D365 import files per plant.
Users: factory requesters + procurement (Peter, 1–2 people)

**Read `docs/HANDOFF.md` first** — status, how to run, and traps already hit.
Backlog: `docs/stories/`. Group standard: `docs/group-standard/`.

Status: core workflow built and tested (113 tests). Not yet open to plants —
STORY-001 (login) must ship first.

## Stack
FastAPI + SQLAlchemy + Alembic | SQLite (dev) / PostgreSQL (prod) | HTMX + Jinja2 | Docker → Render/Railway

## Architecture rules
- routes → services → models; business logic only in services
- Schema changes only via Alembic migrations; read every autogenerated migration
  and verify on a fresh DB (tests use create_all and will not catch a broken migration)
- Every feature ships with tests (happy path + failure path); new tests use `central_ids()`
- Secrets via env vars only; `.env.example` stays current
- Central codes are issued only from `running_register`
- Taxonomy and reference data are data (app/data/*.json, admin pages), never hardcoded logic

## Domain rules (details in HANDOFF §6)
- Never `\b` next to Thai characters; never NFKC on Thai (use NFC + fix_thai)
- Names: `[CATEGORY] - [name] - [detail]`, ≤ 110 chars, units spaced (`20 L`)
- Service requests never get an Item-type category
- Stock code systems stay inactive (out of scope)

## Out of scope for v1
- Direct write to AX/D365 (API/DB) — export files only
- Editing/deactivating existing items
- Approval workflow beyond procurement
- Teams notifications (email + in-web status only)
- Reporting dashboards beyond the request queue
- Stock items (CBD 99xx / 8xx) — owned by the stock team
- Factories beyond CBD, APM, APG, ACM
