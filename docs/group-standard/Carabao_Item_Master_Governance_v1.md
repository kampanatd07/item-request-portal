# Item Master Governance — Carabao Group

> ฉบับร่าง v1 · 6 ส.ค. 2026
> เอกสารนี้ตอบคำถามเดียว: **ทำอย่างไรไม่ให้ master ใหม่กลับไปรกเหมือนเดิมภายในปีเดียว**

---

## 0. ทำไมต้องมี — บทเรียนจากข้อมูลจริง

ข้อมูลรอบนี้บอกสาเหตุที่ master เดิมพัง ชัดเจน 3 ข้อ:

| อาการที่เจอ | จำนวน | สาเหตุเชิงระบบ |
|---|---|---|
| รหัสถูก generate ไว้ล่วงหน้าโดยไม่มีของ | 5,316 (47%) | ไม่มีเจ้าของทะเบียนเลข ใครก็จองบล็อกได้ |
| ของซ้ำกัน เปิดหลายรหัส | 267 · ข้ามโรงงาน 174 | ไม่มีขั้นตอน "ค้นก่อนเปิด" |
| จัดของลงกลุ่มไม่ตรงหมวด | 1,660 | ไม่มีใครตรวจก่อนอนุมัติ |

**ถ้าไม่แก้ 3 ข้อนี้ ปัญหาเดิมกลับมาแน่นอน** — เอกสารนี้แก้ทีละข้อ

## 1. บทบาทและผู้รับผิดชอบ

| บทบาท | ใคร | หน้าที่ | จำนวนคน |
|---|---|---|---|
| **Data Owner** | หัวหน้า Procurement Strategy | เจ้าของนโยบาย · อนุมัติการเปลี่ยน taxonomy · ชี้ขาดข้อพิพาท | 1 |
| **Data Steward (กลาง)** | *ยังไม่มี — ต้องแต่งตั้ง* | ดูแลทะเบียนเลขรัน · อนุมัติ item ใหม่ · ตรวจคุณภาพรายเดือน | 1 (+สำรอง 1) |
| **Steward ประจำโรงงาน** | ผู้แทน ACM / APM / APG / CBD | ตรวจคำขอเบื้องต้น · ยืนยันว่าของมีจริง | 4 |
| **Requester** | ใครก็ได้ที่ต้องซื้อ | กรอกคำขอให้ครบ | ทุกคน |
| **ผู้ทวนสอบเทคนิค** | วิศวกรรม / QA / IT ตามหมวด | ยืนยัน spec เมื่อเป็นของเทคนิค | ตามหมวด |

> ⚠️ **ช่อง Data Steward กลางยังว่าง** — ตำแหน่งนี้คือสิ่งเดียวที่กันไม่ให้เลขรันชนกัน
> ถ้าไม่แต่งตั้ง **ห้ามเริ่มเฟส 1 ของ cutover**

## 2. ขั้นตอนขอเปิด Item ใหม่

```
Requester กรอกคำขอ
        ↓
[G1] ค้นก่อนเปิด — บังคับ
        ↓ ไม่เจอของเดิม
Steward โรงงาน ตรวจเบื้องต้น
        ↓
[G2] ตรวจครบถ้วน + จัดหมวด
        ↓ ถ้าเป็นของเทคนิค
ผู้ทวนสอบเทคนิค ยืนยัน spec
        ↓
[G3] Data Steward กลาง อนุมัติ + ออกเลขรันจากทะเบียน
        ↓
Item ใช้งานได้
```

### G1 — ค้นก่อนเปิด (ด่านที่สำคัญที่สุด)

**กฎ: ห้ามส่งคำขอโดยไม่แนบหลักฐานการค้น**

Requester ต้องค้นอย่างน้อย 3 แบบ แล้วแนบผลมาด้วย:
1. ค้นด้วย**ชื่อสามัญภาษาไทย** (เช่น "ลูกปืน")
2. ค้นด้วย**ชื่ออังกฤษ/ยี่ห้อ/รุ่น** (เช่น "bearing SKF 6205")
3. ค้นด้วย**รหัสเดิม** ถ้าเคยซื้อ

> เหตุผลที่ต้องค้น 3 แบบ: ชื่อเป็น Hybrid ไทย/อังกฤษ ค้นแบบเดียวมักไม่เจอ
> 174 รายการที่ซ้ำข้ามโรงงานรอบนี้ เกิดจากไม่ค้นข้ามโรงงานทั้งนั้น

### G2 — ข้อมูลที่ต้องครบก่อนส่งต่อ

| ฟิลด์ | บังคับ | หมายเหตุ |
|---|---|---|
| ชื่อตาม naming convention | ✅ | `[CATEGORY] - ชื่อ - รายละเอียด` ไม่เกิน 110 ตัวอักษร |
| Item Group + Sub-Category | ✅ | ต้องอยู่ใน taxonomy 20/105 เท่านั้น |
| Base UoM | ✅ | ต้องอยู่ใน UoM master |
| Purchase UoM + Pack size | ✅ | ถ้าต่างจาก Base UoM |
| ยี่ห้อ / รุ่น / Part number | ⬜ | บังคับถ้าเป็นอะไหล่หรือของเทคนิค |
| ผู้ขายอ้างอิง | ⬜ | ช่วยตรวจของซ้ำ |
| เหตุผลที่ของเดิมใช้ไม่ได้ | ✅ | **ถ้าค้นแล้วเจอของใกล้เคียง** |

### G3 — Data Steward กลาง

- ตรวจซ้ำว่าไม่ซ้ำของเดิม (ด่านสุดท้าย)
- ตรวจว่าหมวดถูกต้องตาม **"ของนี้คืออะไร" ไม่ใช่ "ใครซื้อ"**
- **ออกเลขรันจากทะเบียนกลาง** — เป็นคนเดียวที่ทำได้
- SLA: อนุมัติภายใน **2 วันทำการ** · ถ้าเกิน escalate ถึง Data Owner

## 3. ทะเบียนเลขรันกลาง — กฎเหล็ก

โครงสร้างรหัส: `[Group 3][Sub 2][Type 2 = 00][Running 4]`

| กฎ | รายละเอียด |
|---|---|
| **1 ทะเบียน ต่อ 1 คู่ (Group + Sub)** | เลขรันเดินอิสระในแต่ละคู่ |
| **ออกเลขได้คนเดียว** | Data Steward กลางเท่านั้น |
| **ห้ามจองบล็อกล่วงหน้า** | ← กฎที่กันไม่ให้เกิด 5,316 รหัสผีซ้ำ |
| **ห้ามใช้เลขซ้ำแม้ item ถูกลบ** | เลขที่ออกแล้วถือว่าใช้ถาวร |
| **Item Type = `00` เสมอ** | สงวนไว้ขยายอนาคต ห้ามใช้ในเฟสนี้ |
| **เลขรันเต็ม 9999** | ต้องขออนุมัติ Data Owner เพื่อเปิด Sub-Category ใหม่ |

**สิ่งที่ต้องมีก่อน go-live:** ไฟล์/ตารางทะเบียนที่บันทึก — เลขล่าสุดของแต่ละคู่ · ใครออก · วันที่ · ให้ item ไหน

## 4. การเปลี่ยนแปลงหลัง item ถูกสร้าง

| อยากเปลี่ยน | ใครอนุมัติ | เปลี่ยนรหัสไหม |
|---|---|---|
| แก้คำผิดในชื่อ | Steward โรงงาน | ไม่ |
| เพิ่มรายละเอียด spec | Steward โรงงาน | ไม่ |
| แก้ UoM | Data Steward กลาง | ไม่ (แต่ต้องเช็ค PO ค้าง) |
| **ย้าย Sub-Category** | Data Steward กลาง | **ใช่ — ออกรหัสใหม่** |
| **ย้าย Item Group** | Data Owner | **ใช่ — ออกรหัสใหม่** |
| เลิกใช้ | Steward โรงงาน | ไม่ — ตั้ง `Blocked` |

> **ห้ามลบ item ออกจากระบบเด็ดขาด** ใช้ `Lifecycle = Blocked` เสมอ
> เหตุผล: ประวัติ spend ต้องอ่านย้อนหลังได้ตลอดไป
> **ห้ามใส่คำว่า "(ยกเลิก)" ในชื่อ** — ใช้ฟิลด์ Lifecycle เท่านั้น

## 5. KPI วัดคุณภาพ (รายงานรายเดือนถึง Data Owner)

| KPI | สูตร | เป้าหมาย | ทำไมวัด |
|---|---|---|---|
| **% Clean** | item ที่หมวดย่อยไม่ใช่ `99` ÷ ทั้งหมด | ≥ 85% | ตอนนี้ **77.2%** |
| **% ที่ยังอยู่ในหมวด Other** | sub = `99` ÷ ทั้งหมด | ≤ 15% | ตอนนี้ **21.3%** |
| **อัตราของซ้ำ** | item ซ้ำที่ตรวจพบ ÷ item ใหม่ในเดือน | ≤ 1% | วัดว่า G1 ทำงานจริงไหม |
| **% UoM ที่ยืนยันแล้ว** | UoM Source ≠ Default ÷ ทั้งหมด | 100% | ตอนนี้ **12.9%** ⚠️ |
| **เวลาอนุมัติเฉลี่ย** | วันที่อนุมัติ − วันที่ขอ | ≤ 2 วันทำการ | ถ้าช้า คนจะเลี่ยงกระบวนการ |
| **% คำขอที่ถูกตีกลับ** | ตีกลับ ÷ คำขอทั้งหมด | 10-20% | **ต่ำเกินไปแปลว่าไม่ได้ตรวจจริง** |

**ทบทวน taxonomy ปีละครั้ง** — ดู Sub-Category ที่ไม่มีของเลย และ `99 Other` ที่บวมผิดปกติ
