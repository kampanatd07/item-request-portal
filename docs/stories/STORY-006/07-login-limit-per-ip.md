# 07: Login refuses a client IP after 50 failures in 15 minutes

Status: in-progress (waiting for CI)
Triage: ready-for-agent
Parent: STORY-006 (part A)
Blocked by: 01, 06

**What to build:** password spraying (one password across many emails) is
stopped at the door (AC 5; built in the app, decisions.md 2026-10-21). Each
failed login (unknown email, wrong password, locked, deactivated) counts
against the client IP from ticket 06. 50 failures within a 15-minute window
block that IP for 15 minutes; a window older than 15 minutes starts again
from zero; a success does not reset the count. A blocked IP gets HTTP 429
and the login page with "มีการเข้าสู่ระบบผิดจากเครื่องนี้หลายครั้งเกินไป
กรุณารอ 15 นาทีแล้วลองใหม่", before any password hashing. Counts live in a
new table (row locked `FOR UPDATE`; survives restarts and processes); rows
idle for over a day are removed when a failure is recorded. The block is
logged once, with the IP and no password. The per-email lockout stays; both
apply.

The login form is a plain form POST (no HTMX, no `hx-boost`; checked
2026-10-21), so the browser shows the 429 page as it is and
`htmx:beforeSwap` needs no change. If the login form ever moves to HTMX, 429
must be added there.

## Notes (2026-10-22)

Decisions (Peter, 2026-10-22): the IP row stays locked through the password
hashing (strict count; ~65 ms Argon2 per attempt at production cost, so
logins from one IP queue one after another); lock order IP row → Account
row everywhere; the 50th failure gets the normal 401 and starts the block,
the 51st gets 429 (like the per-email lock); tidying old rows runs in its
own short transaction after the login commits, `SKIP LOCKED`, and its
failure never fails the login.

- Table `login_ip_failures` (migration `d7601fa1002b`, autogenerated, read
  line by line: only the new table; upgrade → downgrade → upgrade + seed on a
  fresh SQLite DB OK; PostgreSQL and the drift check run in CI).
- `auth.authenticate(..., client_ip=)` is keyword-required, so no caller can
  forget it; the route passes `request.client.host` as the proxy layer left
  it. Anything that is not an IP is stored as one bucket, `unknown`.
- Blocked → `IpBlocked` before any hashing → the route answers 429 with
  "มีการเข้าสู่ระบบผิดจากเครื่องนี้หลายครั้งเกินไป กรุณารอ 15 นาทีแล้วลองใหม่".
  The login form is a plain POST (guard test), so no `htmx:beforeSwap` change.
- Every failure kind counts (unknown email, wrong password, locked,
  deactivated); a success does not reset. Block logged once:
  `login_ip_blocked ip=… until=…` on `app.accounts`, no password.
- Tests: `tests/test_login_ip_limit.py` (19, SQLite through `POST /login`,
  including one through the real `ProxyHeadersMiddleware` wrapping the real
  app, per the ticket 06 review note 7) and `tests/test_pg_login_ip_limit.py`
  (2, PostgreSQL: 80 parallel failures from a new IP → exactly 50 counted, 30
  blocked; parallel failures across 4 emails × 3 IPs → no deadlock).

**Browser check (Peter).** Once: `alembic upgrade head` on the dev DB. Start
the app with `start.bat`, then in PowerShell:

```powershell
1..50 | ForEach-Object { try { Invoke-WebRequest -Uri http://127.0.0.1:8000/login -Method Post -UseBasicParsing -Body @{ email = "spray$_@test.local"; password = "wrong-password" } | Out-Null } catch {} }
```

Then open **http://127.0.0.1:8000/login** (not `localhost`, which may go
over IPv6 `::1`, a different IP) and log in: the Thai message above shows.
The block lasts 15 minutes; your own Account is not locked (the 50 attempts
used made-up emails).
